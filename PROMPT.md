# Loop prompt — invariant

Do not edit this file during a run. It must be the same bytes every iteration.

---

You are working on Harmonic. Read `CLAUDE.md` first; its invariants and its "never touch" list are
binding.

## Your task this iteration

1. Open `fix_plan.md`. Take the **single** highest-priority item whose status is `TODO`. If every
   item is `DONE` or `BLOCKED`, go to **Conformance reached** below and stop.
2. Read **only** the one spec file that item names, at `openspec/specs/<capability>/spec.md`. Do not
   read the design documents — they are prose and history, they describe features that were
   deliberately removed, and they are not the contract.
3. Implement the **smallest** change that satisfies the named scenarios. Search the codebase before
   writing anything new; a component for this probably exists in `app/src/ui/`.
4. Add or extend a test in `app/tests/` that fails before your change and passes after it.
5. Run `bash scripts/gate.sh`.
   - **Green:** go to step 6.
   - **Red:** fix the implementation and run it again. After **three** consecutive failures on this
     same item, set its status to `BLOCKED`, append the actual failure text to `loop-log.md`, and
     stop. Do not move to another item in the same iteration.
6. Append one entry to `loop-log.md`:
   `date · item id · files touched · gate result with the real numbers · tokens and wall-clock`.
7. Set the item's status to `DONE` in `fix_plan.md`, commit on a branch named `loop/<item-id>`, and
   open a pull request. **Do not merge.** Stop.

## Rules

- **One item per iteration.** Finishing early is not a reason to start another.
- **Never edit `openspec/specs/**`.** If the spec is wrong, or is the thing stopping you, go to
  **The spec is the obstacle** below.
- **Never touch** anything in `CLAUDE.md`'s "never touch" list. If an item seems to require it, the
  item is misclassified: mark it `BLOCKED` with the reason and stop.
- **Never weaken a test, a threshold or the gate** to get green. If the gate is wrong, say so in
  `loop-log.md` and stop; a human will decide.
- No placeholders, no `TODO`, no commented-out code, no new dependencies.
- No new features. Every item is parity, consistency, continuity or correctness against a spec that
  already exists.

## The spec is the obstacle

If the implementation already satisfies every scenario and the item still cannot be completed, or the
spec contradicts shipped behaviour, then **stop** and write
`openspec/changes/spec-change-<capability>-<date>/proposal.md` containing:

```markdown
## Conformance status
Which scenarios are MET, the gate result with its real numbers, and the commit.

## Why the spec now limits progress
The exact requirement text, and what the code does instead.

## Proposed amendment (NOT APPLIED)
ADDED / MODIFIED / REMOVED Requirement blocks, in OpenSpec delta form.

## Open questions for the human
[NEEDS CLARIFICATION: ...]
```

Then stop. Do not apply the amendment. Do not continue to the next item.

## Conformance reached

Every item is `DONE` or `BLOCKED` and the gate is green. Write a short summary to `loop-log.md`:
which items landed, which are blocked and why, the gate's numbers, and what the next backlog should
contain. Then stop. Do not invent new work.
