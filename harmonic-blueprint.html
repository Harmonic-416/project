Product Design Blueprint · Progressive Web App

Harmonic — a practice room that listens back

Translating the Harmonic user-story map into the diagrams you actually build a PWA from: an information architecture, the core interaction flows, and the offline-first system that powers live feedback.

01 The question, answered

Which diagram should we follow?

A story map tells you what to build. It is not a design you can build a screen from. For a PWA you need three companion diagrams, in this order.

1 · Information Architecture (sitemap). Turns your four user goals into a navigation model — the screens and how a person moves between them. This is your primary blueprint.

2 · User-flow diagrams. One per critical journey (e.g. choose song → view tabs → play with live feedback → review score). These validate that every story-map card has a home.

3 · System / PWA architecture. The technical diagram unique to a PWA: app shell, service worker, offline cache, and the real-time audio pipeline behind “live feedback.”

The sections below deliver all three, plus screen blueprints and a build roadmap.

03 Primary diagram · Information architecture

The navigation map

Mobile-first PWA convention: a persistent bottom tab bar of 3–5 destinations, each a shallow stack. Your four goals fold into Practice and Progress, with a shared Library feeding both.

Why not one tab per goal? Four goal-tabs would duplicate “choose a song” and “view a score” twice each. Grouping by verb (find → practice → review) instead of by instrument keeps the nav to four items and lets guitar and voice share every screen.

05 The abstraction · Guitar & Singing

Share the core, fork two thin adapters

The real design decision: how much of guitar and singing is one system? Answer — nearly all of it. Both are mic → analyze → compare to reference → color the score → record. Only what the analyzer hears and how the notation draws actually differ. So we build one instrument-agnostic core and plug in a small adapter per instrument.

Verdict: One PWA, one shared core — not two apps, not one tangled app. Guitar and singing run on the same infrastructure; each instrument supplies only a note detector and a notation view (≈15% of the code) behind fixed contracts. Everything else is written once.

Build once Shared core

Instrument-agnostic. Neither guitar nor voice code touches this — it talks only to the contracts below.

  • Audio capturegetUserMedia → AudioContext → AudioWorklet frames
  • Session state machinecount-in · play · pause · scroll · end — identical for both
  • Scorercompare(detected, expected) → feedback events + accuracy %, config-tuned per instrument
  • Recording & storageMediaRecorder → IndexedDB (recordings, scores, annotations)
  • Library, search, Progress, PWA shellone data model: a session → score + event log over time

Per instrument Adapters

Two small modules each, implementing a shared interface. This is the only code that knows “guitar” or “voice.”

  • Analyzer — detect(frame) → eventsVoice: monophonic pitch (YIN). Guitar: onset + polyphonic / chord detection
  • Notation rendererVoice: scrolling stave. Guitar: scrolling tablature
  • Feedback vocabulary Voice: flat/sharp in cents, breath. Guitar: wrong note/chord, rushing — same event shape, different labels
A

~85% shared

Everything but the analyzer and renderer is written once. Adding a third instrument later = two new adapters, not a new app.

B

Not fully merged

No if (guitar) branches scattered through the core — instrument logic is quarantined behind the ports, so the two can evolve independently.

C

Not fully separate

Two codebases would duplicate recording, storage, scoring, offline & progress — and drift apart. One core keeps them in lockstep.

07 Build roadmap

Sequence the diagrams into shippable slices

Each phase is a vertical slice that’s demoable on its own — the fastest path to feeling the core loop.

P0
Skeleton
  • App shell + manifest + service worker → installable, offline-loading.
  • Four-tab navigation from the IA map (fig. 3).
  • Static song library with keyword search.
P1
Practice loop
  • Song detail → scrolling tabs / sheet music with pause & tempo.
  • Web Audio capture + MediaRecorder; sessions saved to IndexedDB.
  • Live pitch/timing meter (voice first — monophonic is simpler).
P2
Review loop
  • Session scoring + accuracy trend on the Progress tab.
  • Feedback detail (notes missed, pitch drift) with session playback.
  • Guitar mode: polyphonic onset detection.
P3
Polish & sync
  • Basic lessons + “3 checks” onboarding; vocal annotations.
  • Wake Lock, media-session, haptics, install prompt.
  • Optional cloud sync via Background Sync.

08 Design system starter

Tokens, carried from your sticky notes

The teal / amber / coral of your map become a real palette: teal for identity & “in-progress,” amber for actions, coral for record/live — with green & red reserved strictly for pitch feedback.

Color

Teal #128789 primary · Amber #D9922E action · Coral #DC6A44 live/record · In-tune #3E9B57 · Off-pitch #CF4B36. Both light & dark themes.

Type

Serif display for headings (warmth, musicality), system sans for body, monospace for tablature & data — where character alignment matters.

Layout

Single-column, thumb-reachable, bottom-tab nav. 8px spacing grid. Large touch targets — people tap mid-practice, sometimes with a pick in hand.

Motion

Reserve animation for the scoring overlay & the scrolling score. Everything else stays still — a metronome-steady interface. Respects reduced-motion.
